Issue: Android APK installation fails with Binder null reference
===============================================================

Status
------

Open. Static diagnosis completed. Runtime root cause is not confirmed.

Reported symptom
----------------

Installing the Android APK fails with:

    Attempt to invoke interface method 'android.os.IBinder android.os.IInterface.asBinder()' on a null object reference

The error was reported during installation. It has not been established whether
the failure occurs in the device PackageInstaller, system_server, or application
startup.

Environment limitation
----------------------

This is a historical static diagnosis. Per the current project scope, emulator
debugging, physical-device debugging, installation checks, and runtime
acceptance are not performed for this task.

The app was not launched during this diagnosis. A successful Gradle build is not
treated as a successful install or runtime test.

Relevant project code
---------------------

The Android app uses these integrations:

    - Hilt for dependency injection.
    - Room for the local SQLite database.
    - Retrofit and OkHttp for optional local Backend connectivity.
    - Jetpack Compose for the UI.

The app-owned Application class only contains @HiltAndroidApp.
MainActivity is a normal exported launcher Activity and does not bind to a
service.

The source AndroidManifest declares only:

    - android.permission.INTERNET
    - DutongjianApplication
    - MainActivity

The merged Manifest contains AndroidX-generated components:

    - androidx.room.MultiInstanceInvalidationService
    - androidx.startup.InitializationProvider
    - androidx.profileinstaller.ProfileInstallReceiver

These entries come from dependencies and are not custom Binder code in this
project. No project code directly calls their Binder APIs.

APK evidence
------------

The previously published v0.1.1 release contained:

    - app-debug.apk
    - app-release-unsigned.apk

The unsigned Release APK is not a valid user-installable release artifact. An
unsigned APK can cause device installation tools to fail, and some vendor
installers may expose an unhelpful Binder null-reference error instead of a
clear signature error.

A signed inspection variant was subsequently added:

    - Build variant: inspection
    - APK: app-inspection.apk
    - Package: com.dutongjian.app
    - Version: 0.1.1, versionCode 2
    - minSdkVersion: 26
    - targetSdkVersion: 35
    - APK v2 signature: verified locally
    - SHA-256:
      6271e57ba986075e2391425f249baddb77d516837c2219dd08969b07d3091b86

The inspection variant uses the Android debug keystore for device inspection
only. It is not a production-signed release APK.

What is confirmed
-----------------

    - No direct Binder API usage exists in project-owned source.
    - No custom Android Service or ServiceConnection exists.
    - The source Manifest has a normal launcher Activity.
    - The signed inspection APK passes local APK v2 signature verification.
    - clean assembleDebug succeeds.
    - The reported exception does not appear in the complete build log.

Possible causes
---------------

    1. The unsigned Release APK was selected for installation.
    2. A device/vendor PackageInstaller or system_server Binder failure occurred.
    3. An existing installation with the same package name or a different
       signing key caused a package update/signature conflict.
    4. A device Android version or vendor installer is incompatible with the
       installation path.
    5. An AndroidX startup or Room system component failed at runtime. This is
       only a possibility; there is no device log proving it.

What is not confirmed
---------------------

    - The exact device model and Android version.
    - Whether app-debug.apk, app-release-unsigned.apk, or app-inspection.apk
      was installed.
    - Whether the exception was emitted by PackageInstaller, system_server,
      installd, or the app process.
    - Whether an older com.dutongjian.app installation was present.
    - Whether the failure happens before package installation or after launch.

Current handling
----------------

No emulator or physical-device reproduction is required. The current delivery
acceptance is limited to Backend tests, Android JVM tests, lint, APK builds, and
the generated Release assets. The user downloads the APK and reports any issue
found during their own use; this file remains a historical static diagnosis.

Do not suppress the exception with catch(Exception). The current evidence does
not justify changing application code.
